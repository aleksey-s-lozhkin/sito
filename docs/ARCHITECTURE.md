# Архитектура

## Приложения

| Приложение | Ответственность |
|---|---|
| `documents` | документы, извлечение текста, индексация, поиск, рубрики, история поиска |
| `users` | кастомная модель пользователя, вход по email, подтверждение почты, сброс пароля |
| `config` | настройки, маршруты, health-эндпоинты |

Внутри `documents` намеренно выделены небольшие модули с одной задачей:

- `constants.py` — единые ограничения (рубрики, длины, типы и размер файла) и
  функции проверки. Единственное место, где описаны правила;
- `utils.py` — извлечение и очистка текста; принимает и путь, и файловый объект;
- `chunking.py` — нарезка текста на куски, чистая функция без зависимостей;
- `documents.py` — описание **двух** индексов Elasticsearch: `documents` (целые
  документы) и `chunks` (отрывки) — см. «Поиск отрывков» ниже;
- `signals.py` — индексация, переиндексация отрывков и сброс кэша после
  сохранения (best-effort);
- `rubrics.py` — сборка списка рубрик и его кэш;
- `services/search_service.py` — поиск в веб-интерфейсе (индекс `documents`);
- `services/chunk_service.py` — сборка отрывков и запись в индекс `chunks`;
- `services/embedding_service.py` — векторы текста через Ollama (модель
  `bge-m3`, 1024 измерения);
- `services/summary_service.py` — описание и теги документа языковой моделью;
- `views/views_retrieve.py` — поиск отрывков для потребителей,
  `POST /api/v1/search/retrieve`;
- `rate_limit.py` — ограничение частоты на общем кэше.

## Модель данных

```text
User (users.User)                     Document (documents.Document)
├── email (USERNAME_FIELD, unique)    ├── user           → User (CASCADE)
├── first_name, last_name             ├── rubrics        JSONField, список строк
├── is_active, is_staff, is_moderator ├── text           TextField (извлечённый текст)
├── is_email_verified                 ├── summary        TextField, описание от модели
├── email_verification_token          ├── keywords       JSONField, теги от модели
├── reset_password_token              ├── is_public      BooleanField
└── reset_password_token_created_at   ├── created_date   auto_now_add
                                      ├── file           FileField, documents/%Y/%m/%d/
                                      ├── file_name      исходное имя файла
                                      ├── file_type      pdf | docx | xlsx | txt
                                      └── text_source    file | manual

SearchHistory                         ApiToken (токен потребителя поиска)
├── user → User (CASCADE)             ├── name           кому выдан
├── query                             ├── scope          personal | service
├── results_count                     ├── user → User    только для personal
└── created_at                        ├── prefix         открытая часть значения
                                      ├── key_hash       SHA-256; самого токена в базе нет
                                      └── last_used_at, is_active
```

`summary` и `keywords` заполняет языковая модель, и они могут быть пустыми:
описание — украшение карточки, а не условие работы, поэтому недоступная модель не
мешает документу сохраниться.

`ApiToken` живёт в базе, а не в настройках, потому что кого искать решает токен
(SEARCH-CONTRACT.md, §2). Хранится только хеш: утечка базы не даёт войти
потребителям, а показать значение можно ровно один раз — при выпуске.

Документ — единственный источник правды. Оба индекса Elasticsearch производные:
`documents` пересобирается командой `manage.py search_index --rebuild -f`,
`chunks` — командой `manage.py reindex_chunks`; любой из них можно удалить без
потери данных. Оговорка про вектора — в разделе «Поиск отрывков».

Ограничения заданы в `documents/constants.py`: до 10 рубрик, до 100 символов в
рубрике, до 100 000 символов текста, файл до 20 МБ одного из четырёх типов.
Лимит файла совпадает с `client_max_body_size` в nginx.

## Создание документа

```text
POST /documents/create/ (или /api/documents/)
  → проверка частоты запросов (Redis; при отказе — пропуск, fail-open)
  → проверка рубрик, текста и файла (documents/constants.py)
  → извлечение текста из загруженного файла (utils.py)
  → одна запись Document в PostgreSQL
  → ответ 302 (веб) или 201 (API)
  ─── после коммита транзакции ───
  → индексация документа в `documents`   (ошибка только в лог)
  → переиндексация отрывков в `chunks`   (ошибка только в лог)
  → сброс кэша рубрик владельца          (ошибка только в лог)
  → описание и теги моделью — отдельным потоком, если описания ещё нет
```

Текст извлекается **до** сохранения, из самого загруженного файла. Раньше
документ записывался дважды: сначала пустой, потом с текстом, прочитанным обратно
с диска по пути `MEDIA_ROOT` — и при несовпадении пути текст молча оставался
пустым.

Описание документа считается в отдельном потоке, а не в `on_commit`: ответ на
загрузку не должен ждать модель 1–5 секунд, а очереди задач в проекте нет.
Потерять эту работу не страшно — команда `summarize_documents` доберёт.

Векторов среди записанного нет намеренно: их считает отдельная команда
`embed_chunks`. Причина в разделе «Поиск отрывков».

## Почему индексация best-effort

Автоматические сигналы `django-elasticsearch-dsl` пишут в Elasticsearch без
обработки ошибок, и исключение выходит прямо из `Document.save()`. При
недоступном Elasticsearch создание документа отвечало 500, хотя строка в
PostgreSQL уже была вставлена.

Поэтому:

- в описании индекса стоит `ignore_signals = True`, а в настройках —
  `ELASTICSEARCH_DSL_AUTOSYNC = False`: библиотека в реальном времени не пишет;
- индексация выполняется в `documents/signals.py` через `transaction.on_commit`
  и любые ошибки оставляет в логе;
- `search_index --rebuild` при этом работает как раньше: он не зависит от
  сигналов.

Обратная сторона: индекс может отстать от базы. Документ, созданный при
недоступном Elasticsearch, найдётся только после переиндексации — состояние
видно в `/health/ready/` как `elasticsearch: degraded`.

## Поиск в веб-интерфейсе

**Путей поиска два, и путать их не стоит** — на этом уже терялось время.
Этот раздел — про путь человека: `documents/views`, индекс `documents`, полный
текст документа. Второй путь — `/api/v1/search/retrieve` для Семёна и лаптя:
индекс `chunks`, гибридный поиск, отдельный раздел ниже.

```text
POST /search/results/ (или /api/search/)
  → multi_match по text и rubrics, fuzziness=AUTO, operator=or, 70 %
  → фильтр доступа: свои документы или публичные
  → фильтры по рубрике и приватности
  → сортировка в Elasticsearch: _score | -created_date | created_date
  → пагинация, подсветка фрагментов
  → запись в SearchHistory (только первая страница)
```

`operator=or` и `minimum_should_match=70%` здесь мягче, чем в поиске отрывков
(`and`, 70 %): человеку нужен ответ на вопрос своими словами, а найденный не тот
документ он видит и отбрасывает сам. Замер вариантов поиска эту ручку не менял —
она вне его области (RAG-EXPERIMENT.md, «Что НЕ делаем»).

Сортировка выполняется Elasticsearch, а не списком результатов в Python: иначе
упорядочивалась бы только текущая страница, а не весь найденный набор.

Сервис поиска возвращает `SearchResponse` с результатами и метаинформацией, а
представления решают, что показать при отказе Elasticsearch: веб-интерфейс
показывает «Поиск временно недоступен», API — ошибку.

## Кэш

Кэшируется только список рубрик — под ключом `rubrics_user_<id>` с TTL 300 секунд.
Страница целиком не кэшируется: `cache_page` без `vary_on_cookie` отдавал одному
пользователю разметку, собранную для другого, вместе с чужими названиями рубрик.

Ключ явный, поэтому сбрасывается через `cache.delete` на любом бэкенде. Прежняя
инвалидация опиралась на Redis-специфичный `delete_pattern` и на фиктивные ключи
`cache_page`, которые никогда не совпадали с реальными.

## Отказы зависимостей

| Что упало | Что происходит |
|---|---|
| PostgreSQL | приложение не работает, `/health/ready/` отдаёт 503 |
| Redis | кэш и лимиты не работают, лимиты пропускают запросы (fail-open), `/health/ready/` — `degraded` |
| Elasticsearch | документы создаются и читаются, поиск отвечает «временно недоступен», `/health/ready/` — `degraded` |

Проверки на эти сценарии — `tests/test_resilience.py`.

## Версия клиента Elasticsearch

Сервер — Elasticsearch 8.11, клиент — `elasticsearch` 7.17 и
`elasticsearch-dsl` 7.4. Ветка 7.17 официально совместима с сервером 8.x, и
`dense_vector` с kNN через неё **работают** — проверено на живом индексе. Но не
через DSL:

- `knn` — параметр верхнего уровня, а не clause: `search.query("knn", ...)`
  отвечает `UnknownDslObject`, а `.extra(knn=...)` роняет клиент. Поэтому
  векторный запрос собирается телом — `views_retrieve.py::_knn_body`;
- при включённой безопасности Elasticsearch 8 (xpack) потребуются креды, которых
  в настройках сейчас нет вовсе.

Обновление клиента до 8.x — отдельная работа, и она **больше не условие для
векторного поиска**: так считалось раньше, пока kNN не проверили телом запроса.

## Что дальше

- **Обновление клиента Elasticsearch до 8.x** — чтобы `knn` стал обычным clause,
  а не телом запроса, и чтобы можно было включить безопасность xpack.
- **Порог релевантности** (`VECTOR_MIN_SCORE`) не выставлен: замер не нашёл ему
  оправдания. Нужен новый замер, а не догадка.
- **Два вопроса, которые не находит ни один вариант** поиска: «как сделать
  короткую функцию без имени» (лямбда-функции) и «как повторить действие
  несколько раз» (цикл for). На перефразированных это предел 5/7.
- **Сканы не отсеиваются при загрузке.** Из файла без текстового слоя получается
  пустой документ, и человек не понимает, почему материал не находится. Для
  одного такого документа уже есть описание по заголовкам
  (`describe_unreadable_documents`), общей проверки нет — PDF-EXTRACTION.md, §4.

## Поиск отрывков для потребителей

Форма границы зафиксирована в [SEARCH-CONTRACT.md](SEARCH-CONTRACT.md): потребителей
двое — Семён (служебный токен, только публичные документы) и лапот (персональный
токен, свои и публичные). Форма — решение, а не предложение: меняется вместе с
потребителями.

- **Куски в отдельном индексе `chunks`.** Один документ даёт десятки кусков,
  поэтому они лежат не в индексе `documents`, а рядом. Индекс производный:
  пересобирается командой `manage.py reindex_chunks` из текста документов и
  обновляется в `transaction.on_commit` вместе с документом.
- **Нарезка** — `documents/chunking.py` (чистая функция без зависимостей),
  сборка кусков — `documents/services/chunk_service.py::build_chunk_payloads`
  (тоже чистая, поэтому проверяется без Elasticsearch).
- **Чем ищет: BM25 плюс вектора, слияние по рангам.** Полнотекстовая половина
  строгая — `operator=and`, `minimum_should_match=70%`, `fuzziness=AUTO`, поля
  `text^3` и `title^2`; векторная — kNN по полю `dense_vector`. Слияние —
  Reciprocal Rank Fusion: складываются **места** (`1 / (60 + место)`), а не очки.
  Почему так: BM25 и косинус живут на разных шкалах, складывать их напрямую —
  складывать метры с килограммами. Замер на 329 кусках: строгий полнотекст
  10/15, гибрид по рангам **13/15**, слияние по очкам 9/15.
- **Вектор куска** — поле `dense_vector` в индексе `chunks`: 1024 измерения
  (`embedding_service.DEFAULT_DIMS`), `similarity=cosine`, `index=True` (без
  последнего kNN невозможен). Ответ модели при этом сверяется с настройкой
  `OLLAMA_EMBED_DIMS`: два числа должны совпадать, иначе поле в индексе и вектор
  разойдутся, и запись упадёт. В уже созданный индекс поле добавляет команда
  `embed_chunks` через `PUT _mapping` — пересоздавать индекс ради поля не нужно.
- **Порядок команд — ловушка.** `reindex_chunks` пересоздаёт индекс и о векторах
  не знает: после него куски снова без векторов, и `embed_chunks` нужно запустить
  снова. Команда идемпотентна — берёт только куски без вектора, — поэтому
  повторный запуск лишнего не считает. После **смены модели эмбеддингов** нужен
  `--force` (пересчитать существующие вектора), а если у новой модели другая
  размерность — ещё и пересоздание индекса: поле создано под 1024.
- **Кого видно** — решает токен, а не запрос: `user_id` в теле запроса
  отклоняется с 400. Служебный токен видит только `is_public=true`,
  персональный — ещё и документы своего пользователя. В векторной половине
  фильтр видимости стоит **внутри** `knn`: проверено на живом индексе, что
  top-level фильтр kNN игнорирует и возвращает чужие куски.
- **Деградация.** Вектора — дополнение, а не замена: если векторная половина
  недоступна или ничего не нашла, ответ приходит полнотекстовым с
  `source="fulltext"`; если полнотекст ничего не нашёл, а вектора нашли —
  `source="vector"`; сработали оба — `hybrid`. Недоступность Elasticsearch или
  отсутствие индекса отрывков — это `503`, а не пустой список: пустой список
  читается как «ничего нет».
- **Отпечаток версии** (`document_version`) — хеш текста документа. Ответ на
  §8.3 контракта: потребитель видит, что документ изменился и отрывок мог
  устареть, не перезапрашивая всё подряд.
- **`score` в ответе — `null`.** После слияния по рангам это ни BM25, ни косинус,
  а сумма обратных мест: число, которое ничего не значит, хуже его отсутствия.
  Порог отсечения задаётся константой `VECTOR_MIN_SCORE` в
  `documents/views/views_retrieve.py`; сейчас она `None`, то есть порога нет.
  Если её выставить, значение применится к полнотекстовой половине как
  `min_score`. Оговорка про контракт: ключ `score` остался, потому что форма
  ответа согласована с потребителями.
- **Документ без текстового слоя.** Скан, из которого текст не извлекается,
  получает **честную заметку**: о чём документ (по заголовкам разделов) и прямо
  сказано, что основного текста нет и почему. Такой документ находится поиском
  по названиям разделов — см. `docs/PDF-EXTRACTION.md`.
